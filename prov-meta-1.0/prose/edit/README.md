# DPS prov-meta-1.0 Prose — Edit Workspace

This folder is the authoring workspace for the DPS Data Provenance Metadata Version 1.0 specification.
Sources are split across Markdown files in `src/`, one per section or subsection.
The `makefile` drives the full build pipeline via [nide](https://pypi.org/project/nide/), pandoc, and typst.

## One source: the JSON schema

The JSON schema `../../json/data-provenance.json` is the normative definition of the format and the only source of the model.
Everything else that describes the model is generated from it, and `make quality` fails when any of it has drifted:

| Artifact                                  | Generated by              | From                       | Shown in                               |
|:------------------------------------------|:--------------------------|:---------------------------|:---------------------------------------|
| `../../jadn/data-provenance.jadn`         | `bin/derive_jadn.py`      | JSON schema                | section Provenance Information Model Encoding (JADN Encoding) |
| property tables in `src/schema-*.md`      | `bin/derive_tables.py`    | the JADN file              | section Provenance Schema              |
| YAML outlines in `src/data-model-*.md`    | `bin/derive_outlines.py`  | JSON schema                | section Provenance Data Model Encoding |
| `src/images/metadata.{dot,svg}` (figure)  | `bin/derive_figure.py`    | JSON schema (via the JADN derivation) | section Provenance Schema   |
| `../../yaml/data-provenance.yaml`         | `bin/derive_yaml.py`      | JSON schema                | section Provenance Information Model Encoding (YAML Encoding) |

The JSON schema carries what the views need beyond validation as annotations, which do not affect validation:
member and type `description`s (the wording of the tables), `x-jadn-type` (the JADN type name of a schema node) and
`x-jadn-enum` (the description of each enumeration value).
To change a description, a type name, a member, or its order, edit the JSON schema and run `make derive`; never edit
the generated files or the tables and outlines directly.

The three model sections follow the same precedence in the document:
first the information model encodings (the roles of the artifacts, JADN, YAML), then the data model encoding
(the member sections with their outlines), then the provenance schema (the figure and the property tables).

## Folder layout

| Path       | Contents                                                              |
|:-----------|:----------------------------------------------------------------------|
| `src/`     | One Markdown file per section; the canonical authoring surface        |

### `etc/` files

| File                            | Purpose                                                           | Edit?        |
|:--------------------------------|:------------------------------------------------------------------|:-------------|
| `nide.yaml`                     | nide pipeline configuration (channels, paths, options)            | yes          |
| `bind.txt`                      | Assembly order — lists source files in document sequence          | yes          |
| `dps.typ`                       | Typst document template (DPS-specific layout)                     | yes          |
| `oasis.typ`                     | Typst OASIS branding and style definitions                        | yes          |
| `section-display-to-label.json` | Maps display numbers to section labels                            | **yes**      |
| `section-label-to-display.json` | Inverse of the above; derived by `nide harvest`                   | no — derived |
| `section-display-to-text.json`  | Maps display numbers to section titles; derived by `nide harvest` | no — derived |
| `example-global-to-local.json`  | Maps global example IDs to per-section local IDs                  | **yes**      |
| `example-local-to-global.json`  | Inverse of the above; derived by `nide harvest`                   | no — derived |
| `rules/oasis.rules.yaml`        | Shared OASIS publication-assurance baseline quality rules         | no — upstream|
| `rules/spec.rules.yaml`         | DPS prov-meta spec-specific quality rules; extends oasis baseline | yes          |

**Mapping file discipline:** the two files marked **yes** above are hand-edited.
Their inverses are regenerated by `nide harvest` (the `make sections` target) every time a build runs.
Never edit the derived files directly — your changes will be overwritten on the next build.

**`oasis.rules.yaml`** is a verbatim copy from the `OASIS-Docs/publication-assurance` repository.
Do not edit it locally; update it by copying the upstream version when a new release is available.

### `bin/` scripts

| Script               | Purpose                                                                                |
|:---------------------|:---------------------------------------------------------------------------------------|
| `derive_jadn.py`     | Derives the JADN information model from the JSON schema                                |
| `derive_tables.py`   | Derives the property tables (and their `\columns=` widths) from the JADN model          |
| `derive_outlines.py` | Derives the body of every `{.yaml json-path="..."}` fence from the JSON schema          |
| `derive_figure.py`   | Derives the overview figure (Graphviz source and SVG) from the JSON schema              |
| `derive_yaml.py`     | Derives the YAML serialization of the JSON schema                                      |
| `patch.py`           | Applies YAML-configured text patches to generated output files                         |

Every `derive_*.py` rewrites its artifact when run plain, and with `--check` reports drift as a diff and exits 1.

**JADN** (`derive_jadn.py`): the type order is the root, then the types of each top-level member depth first,
then the types shared by more than one top-level member, then the string aliases.
The string formats `uri`, `uuid`, `date-time` and `date` become the aliases `URI`, `UUID`, `DateTime` and `Date`.

**Property tables** (`derive_tables.py`): each table is found by its caption line (`` Table: Type `Name` (Kind){#tab:...} ``)
and regenerated with the `\columns=` line before it; the prose between the tables stays.
Every JADN type except the four format aliases needs exactly one table: for a new type, add its caption line where
the table belongs (after a table row, as the existing ones), then run `make derive`.
Column widths are one set per table shape (members, enumeration items, simple types): identifier columns are as
wide as the longest identifier of that shape, so code values never wrap in the PDF; the description takes the rest.

**Figure** (`derive_figure.py`): the root type and the type of each top-level member with all members, in the
vocabulary of the tables. The drift check compares `metadata.dot`; Graphviz `dot` renders `metadata.svg` from it.

The YAML outlines in the data model sections are derived, never edited:
the JSON schema (`pi.json-schema` in `etc/nide.yaml`) is the source, and the JSON path of each fence selects what it shows.
A path ending in `properties` shows the members of that object; any other path shows the member it addresses, expanded
(a facet keyword such as `pattern`, `format`, `enum` or `$ref` selects the member it constrains).
Members are listed required first, then optional ones marked `# optional`; other members of the levels above are elided as `# ...`.
To change an outline, change the schema or the fence's JSON path, then run `make derive` (or `make outlines` alone).

## The authoring loop

    # 1. Edit one or more source files (prose), or the JSON schema (model)
    $EDITOR src/some-section.md
    $EDITOR ../../json/data-provenance.json

    # 2. After a schema change, re-derive JADN, tables, outlines, figure, and YAML
    make derive

    # 3. Build HTML to review locally
    make html

    # 4. Check document completeness against editorial rules
    make quality       # drift check of all derived artifacts, then per-rule PASS/FAIL/NA report

    # 5. When ready for a round-trip review, build all channels
    make release

    # 6. Verify nothing unintended changed
    make diff          # prose diff of HTML against VCS HEAD
    make diff-repro    # reproducible diff of PDF against VCS HEAD

    # 7. Check VCS status, then commit
    make status

## Build targets

### Primary targets

| Target          | What it does                                                                               |
|:----------------|:-------------------------------------------------------------------------------------------|
| `make release`  | Full build: html + pdf + `nide manifest` + `nide validate`                                 |
| `make html`     | GFM+ and HTML (implies `make gfm-plus`)                                                    |
| `make gfm-plus` | Assembles sources, renders GFM+ markdown and IR                                            |
| `make pdf`      | Assembles sources, renders PDF via typst; copies typst source and checksums to `../share/` |

### Inspection and diff targets

| Target                | What it does                                                                                                    |
|:----------------------|:----------------------------------------------------------------------------------------------------------------|
| `make quality`        | `make check-derived`, then `nide quality` — per-rule PASS/FAIL/NA report against `etc/rules/spec.rules.yaml`     |
| `make validate`       | `nide validate` — checks the outputs in `../share/` against the manifest                                        |
| `make diff`           | `nide diff --mode prose` on the HTML — readable word-level diff against VCS HEAD                                |
| `make diff-repro`     | `nide diff --mode repro` on the PDF — timestamp-normalised diff against VCS HEAD                                |
| `make status`         | `git status` summary                                                                                            |
| `make context`        | Reports clone, branch, revision, and location details                                                           |

### Derivation targets (the JSON schema is the source)

| Target                | What it does                                                                                                    |
|:----------------------|:----------------------------------------------------------------------------------------------------------------|
| `make derive`         | Rewrites all derived artifacts in dependency order: JADN, tables, outlines, figure, YAML                        |
| `make check-derived`  | Reports the drift of every derived artifact as a diff; fails when any differs (run first by `make quality`)     |
| `make outlines`       | Rewrites only the YAML outline fences in `src/`                                                                 |
| `make check-outlines` | Reports only the outline drift                                                                                  |

### Code quality targets (for `bin/` scripts)

| Target        | What it does                  |
|:--------------|:------------------------------|
| `make lint`   | ruff + black check + unmake   |
| `make format` | ruff --fix + black (in-place) |
| `make types`  | mypy                          |
| `make all`    | lint + types + build          |

### Maintenance targets

|:-----------------|:----------------------------------------------------------------|

## Using `nide quality` directly

The make target runs `nide quality` with the rules file configured in `etc/nide.yaml`.
For finer control, run it directly after `make gfm-plus` (which writes `build/ir.json`):

    # default: reads quality.rules from etc/nide.yaml
    nide quality

    # explicit rules file
    nide quality --rules etc/rules/spec.rules.yaml

    # machine-readable output (for CI or scripting)
    nide quality --json | jq '.[] | select(.result == "FAIL")'

    # promote WARN to BLOCKER (strict mode)
    nide quality --strict

The rules file `etc/rules/spec.rules.yaml` extends `etc/rules/oasis.rules.yaml`
(the shared OASIS publication-assurance baseline) and adds DPS prov-meta specific checks.
`oasis.rules.yaml` comes from the `OASIS-Docs/publication-assurance` repository —
copy it from there; do not edit it locally.

## Using `nide diff` directly

The make targets cover the common cases.
For finer control, run `nide diff` directly (VCS version is extracted automatically):

    # prose mode — readable word-level diff
    nide diff --mode prose ../share/prov-meta-v1.0-draft.html

    # repro mode — suppress build-timestamp noise
    nide diff --mode repro ../share/prov-meta-v1.0-draft.pdf

    # meta mode — show only XMP / header metadata changes
    nide diff --mode meta ../share/prov-meta-v1.0-draft.pdf

    # prose diff with XMP block appended
    nide diff --mode prose+xmp ../share/prov-meta-v1.0-draft.html

    # full mode — content + blobs + timestamps + XMP
    nide diff --mode full ../share/prov-meta-v1.0-draft.html

All mode names and modifier names accept unambiguous prefixes (`nide diff --mode pr` is equivalent to `--mode prose`).
